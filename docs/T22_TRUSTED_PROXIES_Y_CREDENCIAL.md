# T22 — TRUSTED_PROXIES y credencial expuesta de Atlas (22–23/10/2026)

## 1. TRUSTED_PROXIES (hecho y verificado en la nube)
**Medición de la cadena real** (eco temporal en la misma red del entorno `dfpub-env`, `dfpub-ipprobe3` con ingreso externo; después se deshabilitó el ingreso, se restauró y quedó en 0 réplicas): el par TCP que ve la aplicación es **`192.168.0.1`** (envoy del entorno) para cualquier cliente; Azure **sobrescribe `X-Forwarded-For` con la IP real del cliente** (una cabecera falsa `X-Forwarded-For: 1.2.3.4, 5.6.7.8` enviada por el cliente **no** llegó a la aplicación; en su lugar llegó solo la IP real `181.66.157.140`). `X-Real-IP` sí llega tal cual, pero la aplicación no lo usa. Antes del cambio `TRUSTED_PROXIES` estaba vacío ⇒ la clave del límite de intentos era el par TCP (`192.168.0.1`), igual para todos los clientes (deducido del código `request.client.host` y de esta medición; no se provocó un bloqueo global para demostrarlo).
**Configuración mínima:** `TRUSTED_PROXIES=192.168.0.1/32` en `dfpub-api` (el middleware `TrustedProxyMiddleware` ya recorre la cadena de derecha a izquierda y solo cree en `X-Forwarded-For` si el par directo está en la lista; un par distinto no es creído). Se añadió al bicep como valor por defecto con la explicación. Para que la réplica lo tomara hubo que bajar a 0 y volver a 1 (un cambio solo de variable no renovó la réplica en este entorno).
**Verificación** (`dfpub-api` nueva réplica `586216f1`, `TRUSTED_PROXIES=[192.168.0.1/32]`, `ping` Atlas ok): desde la IP de salida del contenedor API (`20.226.40.137`) 20 intentos fallidos con usuarios inexistentes → 401 y del 21.º en adelante **429**; con `X-Forwarded-For` falsificado (`203.0.113.9`, `198.51.100.7, 203.0.113.10`) desde esa misma IP sigue el **429** (no se evade); desde otro cliente (esta máquina, IP distinta) un intento fallido da **401**, no 429, incluso enviando `X-Forwarded-For: 20.226.40.137` (no se hereda el bloqueo ajeno). Regresión: recorrido público 12/12; roles/CSRF sin cambios (lector 403 con token válido, administrador 422); HTTPS (301 de HTTP, HSTS, CSP, X-Frame-Options) y cookie HttpOnly/Secure/Strict intactos.
**Vigilancia:** si Azure cambiara la dirección del salto (no es `192.168.0.1`), el sistema vuelve al comportamiento anterior (clave global), sin abrir nada; se detecta porque un cliente distinto recibiría 429 por intentos ajenos. Repetir la medición con el eco tras cambios de plataforma.
